#### Row-level security (Phase 2)

Application filters (`tenantScope`) are the first wall between businesses; Postgres row-level security is the second. Every business table has a policy `"tenantId" = current_setting('app.tenant_id')`, so a query that forgets its filter returns no rows of another business and a write that names another business is refused.

- **How the business reaches Postgres.** `src/lib/db.ts` is a Prisma client extension (`src/lib/tenant-db.ts`): each query runs in a transaction that starts with `set_config('app.tenant_id', <business>, true)`. The setting lasts for that transaction only, so it is safe through a pooled connection (Neon, Supabase, pgBouncer in transaction mode): nothing carries over to the next request. The business comes from `withTenant()` (`src/lib/tenant-context.ts`); `authed()` sets it from the session. A query with no business set is refused by the client (`NoTenantContextError`) and, if it got through, would see no rows.
- **Two clients.** `db` is held back by the policies. `platformDb` (`src/lib/platform-db.ts`) is not: it is for sign-in, tokens, the daily jobs that loop over businesses, and the Stripe webhook before it knows whose payment link it has. Only the files listed in `PLATFORM_USERS` in `tests/tenant-scoping.test.ts` may use it. Work for one business that runs outside a request (a stream read after the handler returns, a job) must re-enter it: `withTenant(id, …)` or `keepTenant()`.
- **Roles (production).** `DATABASE_URL` connects as `crm_app`: not the table owner, no `BYPASSRLS`, no superuser. `DIRECT_URL` (migrations) and `PLATFORM_DATABASE_URL` connect as the owner role that owns the tables, which row-level security does not bind. The migration creates `crm_app` without a login and grants it access; give it one once: `ALTER ROLE crm_app LOGIN PASSWORD '<strong password>';`. If the owner role may not create roles (the migration prints a notice), an administrator runs `CREATE ROLE crm_app LOGIN PASSWORD '…' NOSUPERUSER NOBYPASSRLS;` and then the `GRANT` and `REVOKE` statements at the top of `prisma/migrations/20261031000000_row_level_security/migration.sql`. Later migrations grant their own tables only if `crm_app` already exists when they run, so if the role was created after them (or they printed that notice), also run their grants: `20261101000000_tenant_integrations` (`GRANT SELECT, INSERT, UPDATE, DELETE ON "TenantIntegration"`), `20261102000000_billing` (`GRANT UPDATE ("name", "brandName", "senderName", "updatedAt") ON "Tenant"`) and `20261105000000_stock_thresholds` (`GRANT SELECT, INSERT, UPDATE, DELETE ON "StockThreshold"`), each `TO crm_app`. Without them the app fails on integrations, billing and stock thresholds only. Simplest: create `crm_app` with a login before the first `migrate deploy`, so every grant applies by itself. On start in production the server logs a `[security]` error if `DATABASE_URL` connects as a role the policies do not bind.
- **Local development.** With the single `crm` owner role and no `PLATFORM_DATABASE_URL`, the policies exist but do not bind (the owner is exempt), so the app works exactly as before and only the application filters apply. To exercise the policies locally, create `crm_app` with a login, point `DATABASE_URL` at it, and set `PLATFORM_DATABASE_URL` to the owner URL.
- **Adding a table.** A new business table needs `tenantId`, an index, and the same `ENABLE ROW LEVEL SECURITY` plus policy in its migration, and a `GRANT` to `crm_app`; `tests/tenant-schema.test.ts` fails until the policy is there.
- **What it does not cover.** A foreign key is checked by the database itself, so a row could still point at another business's row; the application refuses that (`assertLinks`, `assertTags`) and reading through the link returns nothing. The platform client, a superuser and the migration role cross businesses by design. A SQL injection would run as `crm_app`, so it would be held to one business.
- **Tests.** `tests/rls.test.ts` runs unfiltered queries as a restricted login and checks reads, updates, deletes, cross-business writes, transactions, row locks, overlapping requests on the pool, and the audit log. It needs a test user that can create roles (CI's is a superuser); on a plain local database it skips itself, and CI refuses to skip. `tests/tenant-routes.test.ts` runs every route under the same restricted login.

#### Per-business integrations (Phase 3)

Each business keeps its own Stripe keys, WhatsApp number and website-form origins in `TenantIntegration`: one row per business and service, the settings as JSON **encrypted** with the same key as the two-step secrets (`MFA_ENCRYPTION_KEY`; rotating it works the same way). The sealed JSON also names its business and service, so a row copied to another business is refused. Code: `src/lib/integrations.ts`.

- **Settings API (admin of the business):** `GET /api/admin/integrations` says what is set up, where each setting comes from (`settings` or `env`) and the addresses to give the outside service; secrets are never returned. `PUT /api/admin/integrations/stripe|whatsapp|lead-form` saves a whole set (validated); `DELETE` removes it. There is no screen yet; Phase 4 adds the admin screens.
- **The original business keeps working unchanged.** Until it saves settings of its own, `tenant_ivycandy` falls back to the old environment variables (`STRIPE_*`, `WHATSAPP_*`, `LEAD_FORM_ORIGINS`) and the old addresses (`/api/webhooks/stripe`, `/api/webhooks/whatsapp`, `/api/public/lead`). No other business ever reads the environment variables.
- **One address per business.** Give Stripe `https://<domain>/api/webhooks/stripe/<businessId>` (events `checkout.session.completed` and `checkout.session.async_payment_succeeded`), Meta `https://<domain>/api/webhooks/whatsapp/<businessId>` with the business's verify token, and the website form `https://<domain>/api/public/lead/<businessId>`. The business comes from the address, never from the payload; each request is verified with that business's own secret. An unknown business and one without settings answer the same (503 for webhooks, 404 for the form).
- **Webhook throttle.** The Stripe, WhatsApp and billing webhooks are limited to 300 requests a minute per sender address and kind (`LIMITS.webhookIp`, fails open) before any database read. An unconfigured business answers like a bad signature, so the address never reveals who uses what.
- **Why a payment can't land in another business.** A business controls its own Stripe account, so it could sign an event that names another business's payment link. `recordOnlinePayment` therefore refuses any link that does not belong to the business whose webhook received the event, and WhatsApp messages are filed under the business whose app secret signed them.
- **Rate limits** for the website form include the business (`weblead:<id>:<ip>`, `weblead:<id>:all`). The daily cron already runs each business on its own settings.
- **Email sender:** system mail uses the one `EMAIL_FROM`; a business can send its customer mail from its own verified domain (see "Sender address per business").

#### Sign-up and billing (Phase 4)

- **Sign-up is off by default.** Set `SIGNUP_ENABLED=1` to open `/sign-up` (and `POST /api/signup`) to the public. A signup creates a business in status `PENDING` on plan `trial` (`TRIAL_DAYS`, default 14) with its first admin, and emails a 24-hour confirmation link. Nobody can sign in until it is used. Unconfirmed signups are deleted after 7 days by the daily cron. The endpoint is rate limited per address, per email and overall, and answers the same for an email that already has an account (that person gets a notice instead). The sign-up form has a CAPTCHA (Cloudflare Turnstile, free): create a widget at dash.cloudflare.com, Turnstile, and set `TURNSTILE_SITE_KEY` (public) and `TURNSTILE_SECRET_KEY`. The route then refuses a missing, wrong or unverifiable token (`CAPTCHA_FAILED`, 400; if Cloudflare can't be reached sign-ups are refused, not let through), and the page's security policy allows `frame-src https://challenges.cloudflare.com`. With neither key set there is no CAPTCHA (development only); the production env check requires the secret key when `SIGNUP_ENABLED` is on and both keys together. Turning signup on also requires billing to be configured (the production env check enforces it).
- **Sign-up dev link.** With no mail provider, local development can get the confirmation link back in the signup response, but only when `SIGNUP_DEV_LINKS=1` is set (and mail is console-only). Production start-up refuses to boot with it set, so the link can never reach a visitor there.
- **Billing is Stripe Billing on the platform's own Stripe account**, separate from each business's own Stripe (which is how its customers pay it). Set `BILLING_STRIPE_SECRET_KEY`, `BILLING_STRIPE_WEBHOOK_SECRET` and a price id per plan: `BILLING_PRICE_STARTER`, `BILLING_PRICE_PRO`. In that Stripe account add the endpoint `https://<domain>/api/webhooks/billing` for `customer.subscription.created`, `.updated` and `.deleted`. A business subscribes from Settings, Billing (Stripe Checkout) and manages the card or cancels in Stripe's customer portal. A running trial is honoured: Stripe starts charging when it would have ended. **Tax and currencies:** with `BILLING_AUTOMATIC_TAX=1`, Checkout uses Stripe Tax (billing address required, business tax numbers accepted); leave it unset until Stripe Tax is set up. Each plan is one Stripe price with currency options, so the plan is still found by its price id. A business may choose a currency from `BILLING_CURRENCIES`; the amounts shown come from the price, cached for 10 minutes.
- **Plans and limits** live in `src/lib/plans.ts` (the owner's to change): `trial` and `starter` allow 3 users and 1,000 contacts, `pro` 15 and 25,000, and the original business is `internal` (unlimited, never read-only). Creating a user (or reactivating one) or a contact past the limit is refused with `PLAN_LIMIT`. Contacts that arrive from the website form or WhatsApp are not refused, so no customer enquiry is lost.
- **Read-only mode.** An expired trial, or a cancelled subscription whose paid period is over, makes the business read-only: every write through `authed()` returns `READ_ONLY` (403), except `/api/billing*` and `/api/me*`; reading and exporting keep working, and a banner explains it. A failed payment (`PAST_DUE`) keeps working while Stripe retries; cancelling is Stripe's decision. The state is computed from the business row (`accessOf`) and reaches the session within 30 seconds. Customer payments by Stripe link and inbound WhatsApp messages are still recorded for a read-only business (money already taken, messages already sent); the website form is closed (404) for a suspended one.
- **Subscription events** are matched to a business by the Stripe customer id we stored when it first checked out, never by event metadata, and an older event can't undo a newer one (`billingEventAt`).
- **The platform owner's controls** are a script, not a screen: `npm run tenant-admin -- list | suspend <id> | resume <id> | extend-trial <id> <days>`. A suspended business is signed out within 30 seconds and can't sign in.
- **Settings screens** (admin): Business (name, brand and sender name; the brand name is the default for instalment emails), Billing, Integrations (Stripe, WhatsApp, allowed websites). Customer emails can come from the business's own verified domain (Sender address card); everything else uses `EMAIL_FROM`.
- **Tests:** `tests/plans.test.ts` (the rules), `tests/tenant-signup-billing.test.ts` (signup, confirmation, events, read-only, limits on a real database; Stripe is stubbed, so the real Stripe test-mode flow still needs one manual run: sign up, subscribe with a test card, cancel).

#### Deleting a business and message caps (Phase 5)

- **Export.** Admins already have the full export (Settings, Data export): one CSV per area in a zip, with a fresh authenticator code when two-step verification is on. It stays allowed in read-only mode (`/api/export*` is on the read-only allow list).
- **Deleting a business.** Settings, Business, "Delete this business": the admin retypes the business name (and gives an authenticator code if two-step is on). That sets `Tenant.deletionRequestedAt`, emails the admin, and makes the business read-only (reason `deletion_pending`; export and cancelling the deletion still work). The admin can cancel with `DELETE /api/admin/tenant/deletion` any time within 30 days (`DELETION_GRACE_DAYS` in `src/lib/tenant-deletion.ts`).
- **The erasure** runs in the daily cron (`erasedBusinesses` in its response): once 30 days have passed it cancels the business's Stripe subscription (if that fails the erasure is retried the next day), then in one transaction deletes every row in every business table, its users and the business. A test fails if a new business table is missing from `ERASE_ORDER`. What stays: the Stripe customer and its invoices (our tax records live in Stripe) and one `tenant.erased` line in the platform audit trail (name and slug, no personal data). The original (`internal`) business can't be deleted from the app or by the job.
- **Audit log.** It stays append-only. The one exception is the erasure: the migration lets the trigger allow a `DELETE` of a row whose `tenantId` equals the transaction-local setting `app.erasing_tenant`. The app role has no `DELETE` privilege on the table at all, so only the owner role (the platform client) can use it. Backups taken before the erasure still contain the data: set their retention (30 days is a sensible match) and say so in the privacy policy.
- **Daily message caps** (`src/lib/usage-limits.ts`, numbers in `PLANS[...].daily` in `src/lib/plans.ts`, the owner's to change): trial 50 emails and 25 WhatsApp messages a day, Starter 200 and 100, Pro 1000 and 500, the internal business unlimited. They apply to emails and WhatsApp messages a person sends from the CRM (contact email, WhatsApp reply, team invite, sample email) and answer `USAGE_LIMIT` (429). With Upstash Redis configured the count is exact across servers; without it, it is per server instance. The daily reminder digests and customer instalment emails are not capped (they are bounded by the business's own data).
- **Not built (needs a person):** terms of service, privacy policy and data-processing agreement (a lawyer), and an independent isolation review or penetration test. A sign-up checkbox and legal pages can be added once the texts exist.
- **Tests:** `tests/tenant-deletion.test.ts` (request, cancel, grace period, erasure of every table with the other business untouched, the audit-log guard, the caps).

#### Sender address per business

- **What it does.** Settings, Business, "Sender address": an admin enters a domain they own (for example `mail.yourshop.com`) and a name before the @ (`hello`). The CRM registers the domain with Resend, shows the DNS records (SPF and DKIM) to publish at the company that runs the domain's DNS, and the admin presses Verify. Only once Resend reports the domain verified (`Tenant.senderVerifiedAt`) are the business's customer emails sent from `"Display name" <hello@mail.yourshop.com>`: contact emails from the contact page, instalment reminders and the sample email. Until then, and when the address is removed, they use `EMAIL_FROM` as before with the business's display name.
- **Never from the business's domain:** mail about the account itself (invites, sign-in and confirmation links, password resets, billing) always goes from `EMAIL_FROM`.
- **Needs Resend** (`RESEND_API_KEY`); with SMTP only, the card says it is not available. Your Resend plan limits how many domains the account may hold.
- **Protections.** Ownership is proved by the DNS records, not by what the business types. A domain belongs to one business (`Tenant.senderDomain` is unique; the second claim is refused and the stray Resend domain is removed again). Mailbox providers' domains (gmail.com, outlook.com, …), the CRM's own sending domain and its parent are refused, and the name before the @ allows only letters, digits, dot, dash and underscore. The verified state and domain id are written only by the server as the platform: the business's database role has no grant on those columns, so a business can't mark itself verified. Changing the domain starts verification over and removes the old one from Resend; changing only the name before the @ keeps it.
- **Not handled:** a domain that was verified and later has its DNS records removed is not noticed until Resend refuses to send (the email then fails like any provider failure). Reply-To stays the signed-in user's own address.
- **Tests:** `tests/sender.test.ts` (validation, the verify flow, one domain per business, removal, admin only; Resend is faked, so a real domain verification still needs one manual run).

## Online payments (Stripe)
Payment links are Stripe Payment Links (one payment each, USD and EUR only). The CRM never sees card details.
1. Use **test mode** first. Create a restricted key (`rk_test_…`) that can write *Payment Links*, or a `sk_test_…` key, and put it in `.env` as `STRIPE_SECRET_KEY`.
2. Locally: `stripe listen --forward-to localhost:3001/api/webhooks/stripe` prints a `whsec_…` secret; put it in `.env` as `STRIPE_WEBHOOK_SECRET` and restart the dev server.
3. In production: in the Stripe dashboard add the endpoint `https://<your-domain>/api/webhooks/stripe` (another business: `/api/webhooks/stripe/<businessId>`, see "Per-business integrations") for the events `checkout.session.completed` and `checkout.session.async_payment_succeeded`, and use its signing secret. Switch to live keys only after one real small payment works.
4. `NEXTAUTH_URL` is used for the "thank you" page address (`/pay/result`); outside Vercel it must be your public https URL.
- The webhook (`/api/webhooks/stripe`) is public and protected only by Stripe's signature. A bad signature gets 400; a processing failure gets 500 so Stripe retries. Recording is idempotent (unique `Payment.providerRef`).
- Every online event is in the audit log (`payment.recorded_online`, `payment.online_refund_needed`, `payment_link.created`, `payment_link.cancelled`).
- A payment that can't be recorded (balance dropped, link cancelled, deal deleted) is never dropped silently: link status `REFUND_NEEDED` plus an URGENT task for the deal owner.
- Test cards: `4242 4242 4242 4242`, any future date, any CVC.

### Fast (production-mode) launcher for local use
`start-crm-fast.bat` runs `next build` then `next start` on `CRM_PORT` (default 3001; `CRM_NO_BROWSER=1` skips opening the browser). `scripts/needs-build.ps1` decides whether to rebuild: it compares a marker (`.next\fast-build-done`, written after a successful build) with the source files, and with anything else written into `.next` since, because **the dev server and the build share the `.next` folder** (running `npm run dev` replaces the production files, so the next fast start rebuilds). Never run `next build` while the dev server is up: it overwrites its files. The launcher refuses to start if the port is busy.
It sets `AUTH_TRUST_HOST=true`, `NEXTAUTH_URL=http://localhost:<port>` and `SKIP_ENV_VALIDATION=1` (the startup check in `src/lib/env.ts` is for public deployments and wants Redis, a mail provider and `CRON_SECRET`). Consequences of `NODE_ENV=production`: admins without two-step verification get the Sales-level session (`REQUIRE_ADMIN_MFA` defaults on), `sendMail` throws without `RESEND_API_KEY`/`EMAIL_SERVER` (no console fallback, so invitations and resets fail with a warning), rate limits are in memory. Measured on the seed data (local database): pages 340-500 ms in dev vs 53-64 ms built; APIs 77-117 ms vs 17-48 ms; about 210 KB of compressed JS and CSS per page.

Migrations are hand-written SQL in `prisma/migrations/`. When you change `schema.prisma`, add a matching migration folder, then restart the dev server.

### Tenants (multi-tenancy Phases 0 to 4, see `MULTI_TENANCY_PLAN.md`)

Every business table has a `tenantId` (the business a row belongs to). The original business is `tenant_ivycandy` (`src/lib/tenant.ts`). The tenant work spans these migrations, in this order (later migrations add more tables, each with its own row-level security policy and grants; `prisma/migrations/` is the full, authoritative list):

1. `20261028000000_tenants`: the `Tenant` table, the original business, and `tenantId` on every business table (with a default, so nothing is rewritten).
2. `20261029000000_tenant_uniques`: contact email, organization domain, tag name, template name, invoice number and the automation setting key are unique **per business** instead of across the database. `User.email` stays unique across the database.
3. `20261030000000_tenant_required`: drops the default, so every create must name its business.
4. `20261031000000_row_level_security`: the database refuses cross-business rows itself (see "Row-level security" below).
5. `20261101000000_tenant_integrations`: the encrypted per-business settings table (see "Per-business integrations" below).
6. `20261102000000_billing`: trial and subscription fields on the business, and the `PENDING` status for unconfirmed signups (see "Sign-up and billing" below).
7. `20261103000000_tenant_deletion`: `Tenant.deletionRequestedAt`, and lets the audit log's append-only trigger allow a delete only inside a business's own erasure (see "Deleting a business" below).
8. `20261104000000_sender_domain`: a business's own sending domain and address (see "Sender address per business" below).

In code: the session carries `tenantId`; `tenantScope(user)` (`src/lib/access.ts`) names the caller's business and `ownerScope`/`authorScope`/`taskScope` already include it. Every query on a business table must use one of them. The public entry points (website form, WhatsApp webhook) file leads under `DEFAULT_TENANT_ID` until Phase 3 gives each business its own address.

- **Production / any database that uses migrations:** `npm run db:deploy` applies every pending migration. Back up first.
- **A dev database managed with `db:push`** (no migration history): `db:push` alone fails, because the new foreign keys point at a tenant row that doesn't exist yet. Back up, then run the SQL of each migration you haven't applied, in order, then push:
  1. `npx prisma db execute --file prisma/migrations/20261028000000_tenants/migration.sql`
  2. `npx prisma db execute --file prisma/migrations/20261029000000_tenant_uniques/migration.sql`
  3. `npx prisma db execute --file prisma/migrations/20261030000000_tenant_required/migration.sql`
  4. `npx prisma db execute --file prisma/migrations/20261031000000_row_level_security/migration.sql` (on a plain local database it adds the policies but, lacking CREATEROLE, skips the `crm_app` role with a notice; that is fine for development, see below)
  5. `npx prisma db execute --file prisma/migrations/20261101000000_tenant_integrations/migration.sql`
  6. `npx prisma db execute --file prisma/migrations/20261102000000_billing/migration.sql`
  7. `npx prisma db execute --file prisma/migrations/20261103000000_tenant_deletion/migration.sql`
  8. `npx prisma db execute --schema prisma/schema.prisma --file prisma/migrations/20261104000000_sender_domain/migration.sql`
  9. `npm run db:push` (a no-op that confirms the schema matches), then restart the dev server.
  After `prisma generate` with the new schema, the app errors with "column tenantId does not exist" until these have run.
- **Fresh dev database from `db:push` only:** `npm run db:seed` creates the original tenant before the sample data.
- **New admin in a given business:** `npm run make-admin -- you@example.com --create "Name" --tenant <tenantId>` (default: the original business).
- **Tests:** `tests/tenant-schema.test.ts` and `tests/tenant-scoping.test.ts` always run (the second reads the source and fails when a query on a business table doesn't name the business; exempt files are listed in it with reasons). `tests/tenant-isolation.test.ts` and `tests/tenant-routes.test.ts` need a Postgres: set `TEST_DATABASE_URL` (CI does). They create their own throwaway schema (`tenant_test_…`) and drop it, so they are safe next to real data. The route tests run the real handlers against two businesses and prove one can't reach the other's records.

## Deployment (Vercel)
1. Set the environment variables above in the Vercel project.
2. Build runs `npm run vercel-build` (applies migrations, then builds).
3. Schedule `/api/cron/task-reminders` daily at 08:00 UTC (a Vercel cron or any other scheduler). It needs `Authorization: Bearer <CRON_SECRET>` and sends task and instalment reminders.
4. Check `/api/health` after deploy.

## Troubleshooting
| Symptom | Cause / fix |
|---|---|
| 500 "Unknown field …" or missing new data after a schema change | Stale Prisma client. Run `npx prisma generate` and restart `npm run dev` |
| No emails arrive | No provider set. In dev, emails print to the server console. In production set `RESEND_API_KEY` and a verified `EMAIL_FROM` |
| Reminders never run | `CRON_SECRET` missing or wrong, or cron not enabled on Vercel |
| Invoice import "does nothing" | Invoice number, supplier or billed-to is empty. The error banner is at the top of the form |
| Stock shows items as unmatched | Product, colour and length must match the invoice line (not case-sensitive) |
| A user sees no records | Records are owner-scoped. Only admins see all |
| Data suddenly gone | Someone ran `db:seed` or `db:reset`. Restore from backup |
| Cannot sign in after deploy | Check `NEXTAUTH_URL`, `NEXTAUTH_SECRET`, `AUTH_TRUST_HOST` |

## Backup and restore (PostgreSQL)
- Backup: `pg_dump "$DIRECT_URL" -Fc -f crm.dump`
- Restore into an empty database: `pg_restore -d "<url>" --clean crm.dump`
- Back up before any migration and before deleting sample data. Hosted providers (Neon, Supabase) also offer point-in-time restore.
- Shortcut: `bash scripts/backup.sh` runs the same `pg_dump` into `backups/crm-<timestamp>.dump` (git-ignored; it holds real customer data, so keep it somewhere private).

### Restore drill (do this once before launch, then every quarter)
A backup nobody has restored is a hope, not a backup.
1. Take a backup: `bash scripts/backup.sh`.
2. Create an empty scratch database (a Neon branch, or `createdb crm_restore_test` locally). Never restore over the live one.
3. Restore into it: `pg_restore -d "<scratch url>" --no-owner crm.dump` (use the dump file's real name).
4. Compare row counts: `npm run db:verify -- "<live url>" "<scratch url>"`. It prints a table and exits 1 if any table differs. Counts can differ by a few rows only if people used the app between the backup and the check.
5. Sign in to a copy of the app pointed at the scratch database and open a deal with payments.
6. Delete the scratch database. Note the date in `LAUNCH_RUNBOOK.md`.

### Commands that wipe data
`npm run db:seed` and `npm run db:reset` both refuse unless `DATABASE_URL` points at localhost (and `NODE_ENV` is not production). To override on purpose, pass `--force` **and** set `CONFIRM_WIPE` to the database name, e.g. `CONFIRM_WIPE=crm_staging npm run db:reset -- --force`. Never do this against a database holding real work.

## Money checks (reconciliation)
- **Code:** `src/lib/reconcile.ts`. `reconcileDeal()` is a pure per-deal check; `reconcileTenant()` loads live deals in batches of 500 under the caller's scope. Read-only: it never changes data.
- **Finds:** overpaid deals; instalments or line items that don't add up to the deal amount; online payments with no Stripe reference; paid links with no payment; `REFUND_NEEDED` links; payment links pending over 14 days; won deals that still owe money with no schedule; link/deal currency mismatches. Amounts are shown per deal in the deal's own currency, never summed across currencies.
- **Where:** admins see it as "Money checks" at the top of Reports (`GET /api/reports/reconcile`, admin only). The daily cron (`/api/cron/task-reminders`) also runs it for every active business after the reminders and logs `[reconcile]` warnings (and returns a `reconciliation` summary) when something needs fixing. A failure there never stops reminders. No emails are sent yet.
- **Adding a check:** add a `FindingKind`, a branch in `reconcileDeal()` (its `detail` says what is wrong, with no advice), the plain-words action in the `FIX` map, a label in `KIND_LABEL` (`reports/page.tsx`) and a test in `tests/reconcile.test.ts`.

## Ivy (AI assistant)
Plan and decisions: `AI_ASSISTANT_PLAN.md`. Phase 0 is the groundwork (key, settings, spend ceiling, tables); Phase 1 is the read-only chat and Phase 2 adds proposed actions (both below).
- **Key:** each business adds its own Anthropic key (Settings → Ivy). It is stored like the Stripe and WhatsApp keys (`TenantIntegration`, kind `ANTHROPIC`, encrypted, write-only) and checked with Anthropic when saved (`verifyApiKey` in `src/lib/ai/client.ts`). The original business may use `ANTHROPIC_API_KEY` from `.env` until it saves its own. `anthropicFor(tenantId)` is the only place the key is read.
- **Settings:** `src/lib/ai/settings.ts`, in `AutomationSetting` under the key `assistant`: `enabled` and `monthlyCeilingUsd`. Off by default, and **no default ceiling**: Ivy cannot be switched on without one, and an invalid stored value falls back to off.
- **Spend ceiling:** every model call is recorded in `AiUsage` (tokens and an estimated cost, `src/lib/ai/usage.ts`). The price table is `src/lib/ai/pricing.ts` (an unknown model is billed at the dearest known price, never zero). `assertCanAsk` gates a new question (on, key, ceiling set and not reached, rate limit `LIMITS.assistant`); `assertUnderCeiling` re-checks before each model call. The month is counted in UTC. It is an estimate; Anthropic's invoice is the record.
- **Changing the model or its price:** edit `IVY_MODEL` and `PRICES` in `pricing.ts`, and the cost tests in `tests/ai-pricing.test.ts`.
- **Retention:** `AI_RETENTION_DAYS` (90) in `src/lib/ai/retention.ts`. The daily cron (`runDailyAiRetention`) deletes older conversations (their messages go with them); spend records are kept.
- **Tables:** `AiConversation`, `AiMessage`, `AiUsage`, with row-level security like every business table, and in `ERASE_ORDER` so erasing a business removes them. Messages are kept verbatim (thinking blocks are only valid unedited), so history is never trimmed or summarised.
- **Admin API:** `GET`/`PUT /api/admin/assistant` and `PUT`/`DELETE /api/admin/integrations/anthropic`. Neither ever returns the key.
- **Tests:** `tests/ai-*.test.ts` (no database or network: the Anthropic client is faked), plus `tests/ai-tools-isolation.test.ts`, which needs `TEST_DATABASE_URL` and proves each tool returns only the caller's business.

### Ask Ivy (Phase 1: read-only chat)
- **Where:** the "Ask Ivy" button in the header (or Ctrl/Cmd+K) opens a side panel (`src/components/assistant/ivy-panel.tsx`). Everyone signed in can use it once an admin has switched Ivy on; Ivy only reads what that person can see.
- **The loop:** `src/lib/ai/ivy.ts`. A hand-written streaming loop on `claude-sonnet-5-5` at `low` effort (`IVY_EFFORT`), with adaptive thinking (the default), top-level prompt caching and Anthropic's server-side fallback (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`). Each model call is checked against the ceiling first and recorded after. Caps: 6 tool rounds (`MAX_ROUNDS`) and 50 seconds (`DEADLINE_MS`, inside the route's `maxDuration = 60`). It never throws: every outcome ends in events (`conversation`, `text`, `tool`, `done`, `error`).
- **Tools:** `src/lib/ai/tools/` (`READ_TOOLS`: eleven, all read-only, each a thin wrapper over existing scoped code reading through `ownerScope`/`taskScope`/`authorScope`; `PROPOSAL_TOOLS`: nine, see Proposed actions, Wave B and Phase 3a below). Inputs are validated with Zod; results are capped at 25 rows and 8,000 characters and say when they were cut; internal errors are never shown to the model. A test fails if any tool file calls a write.
- **Instructions and versions:** `src/lib/ai/prompt.ts`. One fixed string for everyone; per-person details (date, business, who is asking) go in the first user message. The model's thinking blocks are only valid if the prompt and tools are unchanged, so each chat stores `IVY_PROMPT_VERSION`, and a chat started under another version can be read but not continued. `tests/ai-prompt.test.ts` pins the version to a fingerprint of the prompt and tool schemas: change either and the test fails until you bump `IVY_PROMPT_VERSION` and the pin (a zod upgrade that changes the generated schemas does the same).
- **Saving:** `src/lib/ai/conversations.ts`. Messages are stored verbatim and append-only; a tool call and its result are written together; a chat ends after 40 stored messages. A chat belongs to one user: every lookup names the business and the user, so admins cannot open other people's chats. Concurrent answers on one chat collide on the message position and the second gets `AI_BUSY`.
- **API:** `POST /api/assistant/chat` (newline-delimited JSON stream), `GET /api/assistant/status`, `GET /api/assistant/conversations`, `GET`/`DELETE /api/assistant/conversations/:id`. All use `authed()` and work in a read-only workspace (`READ_ONLY_ALLOWED`). The chat route writes one audit entry per question with metadata only, never the question; it keeps the business context for the stream with `keepTenant()`.
- **Showing text:** the panel renders Ivy's reply through `src/lib/client/ivy.ts` (`parseBlocks`): paragraphs, lists, bold and links to in-app pages only. No HTML, no images, no external links, so a record cannot make Ivy leak data through a URL. Tested with hostile inputs in `tests/ai-client.format.test.ts`.
- **Prompt injection:** record text (names, notes, messages) reaches the model only as tool-result data, the instructions say never to follow it, and Ivy has no tool that writes or sends, so the worst a hostile record can do is cause a wrong answer.
- **Export:** admins can export spend records (`ai-usage`) and chat metadata (`ai-conversations`: who and when, never titles or text) from Settings → Data export, and both are in the full export.
- **Quality check:** `scripts/ivy-eval.ts` puts 81 questions (including the proposal, Wave B and schedule ones, and a check that the business is exactly as it was afterwards) through the real loop against a made-up business in a throwaway schema (`TEST_DATABASE_URL`). `--dry-run` is free (it checks the expected numbers against the tools). A real run spends money on the key in `ANTHROPIC_API_KEY` and refuses to start without `--budget-usd`; the budget is enforced through Ivy's own ceiling. Run it before changing `IVY_EFFORT`, the prompt or the tools.
- **Changing the prompt or a tool:** edit it, bump `IVY_PROMPT_VERSION`, update the pin in `tests/ai-prompt.test.ts`, run the eval, and note that open chats become read-only.

### Proposed actions (Phase 2)
- **What it is:** Ivy can suggest an action; the person approves it. Nothing changes until they press **Approve**, and Ivy still cannot send anything to a customer. An admin must allow it first (Settings → Ivy → "Allow proposed actions", `proposalsEnabled` in the `assistant` setting, off by default). Until then the proposal tools answer "switched off" and Ivy says so.
- **The five tools** (`src/lib/ai/tools/propose.ts`): `propose_task`, `propose_task_change` (complete, reopen, reschedule, priority, title), `propose_note` (note, call or meeting on a contact or deal), `propose_stage_change` (closing a deal shows a warning) and `draft_message` (text to copy; never sent, never approvable). Each only saves a proposal and tells the model nothing has been done.
- **Kinds:** `src/lib/ai/proposal-kinds.ts`. For each kind, `prepare` checks the model's input against the same Zod schemas and scope checks as the screens (`assertLinks`, `resolveOwner`, `ownerScope`, `taskScope`) and builds the card text from the checked values, never from the model's words; `apply` runs the real action. Add a kind: define its input schema, `prepare`, `apply` and the editable fields, add the enum value (migration), a tool, a line in `TOOL_CHIPS`, and bump `IVY_PROMPT_VERSION`.
- **Shared writes:** `src/lib/crm-actions.ts` (`createTask`, `updateTask`, `logActivity`, `changeDealStage`) is the one place those writes live; the screens' API routes and approvals both call it, so they cannot drift.
- **Lifecycle:** `src/lib/ai/proposals.ts`, table `AiProposal` (RLS, removed with its conversation). A proposal is decided once: approving first claims it with a conditional update (`PENDING` to `APPLIED`), then runs the action, so a double click cannot apply it twice. If the record changed since (a task already done, a deal in another stage, something deleted) nothing is done and the card says why (`FAILED`). If the server dies between the claim and the action the proposal shows as applied with no result: check the record. Proposals expire after 24 hours (`PROPOSAL_TTL_MS`), at most 10 waiting per chat and 30 per person. A person can only see and decide their own.
- **Approval and audit:** `POST /api/assistant/proposals/:id/approve` (optional `edits`, limited to the fields the card shows and validated again) and `/decline`; `GET /api/assistant/proposals?conversationId=`. Approving is refused in a read-only workspace; declining is allowed. Each decision is written to the audit log (`assistant.proposal.approve` / `.decline`, naming what it was).
- **Telling Ivy:** the next question in that chat starts with a `<proposal_outcomes>` note from the CRM saying how each earlier proposal ended (`takeOutcomes`), so Ivy never assumes.
- **Panel:** `src/components/assistant/proposal-cards.tsx`: cards with Approve, Edit and Decline, "Approve all" for several at once (never for ones with a warning), Copy for drafts.
- **Export:** admins can export proposal metadata (`ai-proposals`: kind, status, who, when, never the values).
- **Tests:** `ai-proposals`, `ai-proposal-kinds`, `ai-proposal-routes`, `ai-propose-tools`, and `ai-proposals-isolation` (needs `TEST_DATABASE_URL`: two real businesses).

### Wave B: payments, contacts and deals
- **What it adds:** `propose_payment`, `propose_contact` and `propose_deal` (kinds `PAYMENT_RECORD`, `CONTACT_CREATE`, `DEAL_CREATE` in `src/lib/ai/proposal-kinds.ts`). Same lifecycle as above: Ivy only proposes, the card is built from saved values, approval runs the shared code as the person, once.
- **Payments have their own admin switch** (Settings → Ivy → "Allow payment proposals", `paymentProposalsEnabled`, off by default and only usable once proposed actions are on). Without it `propose()` refuses `PAYMENT_RECORD` with a message Ivy passes on.
- **Payment safeguards:** Ivy passes an amount the person stated and never a currency (an optional `currency` is only compared with the deal's and refused if it differs). The server refuses an invisible deal, zero or negative, an amount above the balance, and a future date. The card shows the balance before and after and the instalment it clears (`summarize` in `src/lib/payments.ts`), warns about the same amount in the last 7 days and about an open payment link, and carries `confirm` text (button "Record 400.00 USD" plus a confirmation dialog). The amount is not editable on the card. Approval calls `recordPayment` (`src/lib/record-payment.ts`) with `expectPaid`: inside the deal's row lock it refuses if anything else was recorded since the card was made. Payment cards are never part of "Approve all".
- **Contacts:** `findDuplicates` warns about a same-name or same-phone match; an exact email match is refused (the database already forbids it). The plan limit (`assertWithinPlan`) is checked when proposing and by `createContact` on approval. Ivy cannot set WhatsApp or email consent flags.
- **Deals:** the total is `itemsTotal(items)`, never supplied by the model; one currency; prices and quantities are required inputs, so Ivy has to ask for them. The stage is always the starting one. Edits on the card are limited to the title and expected close date.
- **Shared writes:** `recordPayment` (`src/lib/record-payment.ts`) plus `createContact` and `createDeal` in `src/lib/crm-actions.ts`; the three API routes call them.
- **Prompt version 3:** rules for payments (only what the person says they received; a customer's claim is not a receipt) and for asking instead of guessing. Chats open before the release are read-only.
- **Tests:** `ai-proposal-money-kinds`, `record-payment`, and the Wave B cases in `ai-proposals-isolation` (including a payment recorded in between, and two approvals at once recording one payment).

### Phase 3a: instalment schedules
- **What it adds:** `propose_schedule` (kind `SCHEDULE_REPLACE`). A schedule drives the customer reminders the daily automations send, so it is treated like a payment: it needs the payment switch ("Allow payment proposals"), shows a confirmation dialog ("Set schedule" / "Replace schedule"), and is never in "Approve all".
- **The CRM does the arithmetic** (`evenSchedule`, `addMonthsUtc` in `src/lib/ai/proposal-kinds.ts`): for "N equal instalments" Ivy passes the count, the first due date and WEEK, TWO_WEEKS or MONTH; the deal total is split with the odd cents on the last instalment and months land on the last day of a shorter month rather than spilling over. A `custom` list is only checked. The split is always of the **deal total**, because payments are applied to instalments oldest-first, so the card shows which instalments existing payments already cover (same `summarize` as the screens).
- **Refused:** an invisible deal, a deal with no amount, fewer than 2 or more than 24 instalments, a zero amount, a total above the deal amount. **Warned:** a total below the deal amount, past dates, and an existing schedule (replacing it clears `InstalmentReminder` history, so customers may be reminded again).
- **Stale guard:** `replaceSchedule` (`src/lib/replace-schedule.ts`, the logic moved out of `PUT /api/deals/:id/schedule`) takes the deal's row lock, and for an approval compares the amount paid and `scheduleKey(...)` of the existing schedule with what the card saw; if either changed it does nothing and the card says so. It keeps the `schedule.replaced` audit entry with the before and after.
- **Tests:** `ai-schedule-kind` (the arithmetic, the card, refusals), `replace-schedule` (lock, scope, stale guard), and the schedule cases in `ai-proposals-isolation` (replaced once, in the right business, two approvals at once, a change in between).

### Phase 3b: the daily "Suggested actions" inbox
- **What it is:** the first time a person uses the app each day, Ivy looks through *their own* records and puts suggestions in a "Suggested" list (the inbox icon in the Ask Ivy panel, with a count on the header button). Each is an ordinary proposal card (Approve / Edit / Decline) with a "Why" line built from data. An admin switch ("Allow daily suggestions", `inboxEnabled`, off by default, needs proposed actions on) turns it on; each person can mute it for themselves (`User.aiSuggestionsMuted`, the link at the bottom of the Suggested list). Nothing is sent to a customer.
- **Rules first, the model second:** `src/lib/ai/inbox/rules.ts` (`findCandidates`) decides what deserves attention with plain queries through the person's own scope: an overdue instalment with no activity or task in the last 3 days (task, plus an email or in-window WhatsApp draft), a Negotiation deal with no activity for 14 days, a won deal with money owed and no schedule (a "agree a payment plan" task: Ivy cannot invent instalment terms), and the person's own tasks overdue by more than 2 days (reschedule to tomorrow). At most 10 candidates a day, ranked by money late, then quiet deals, then plans, then tasks. The existing quiet-lead automation already makes tasks for quiet leads, so there is no second rule for them.
- **Dedupe:** each card has a key (rule, record, ISO week, kind of card), unique per business and person (`AiProposal.dedupeKey`), so the same suggestion is not made twice in a week, even if declined. Suggestions expire after 3 days (`INBOX_TTL_MS`), chat proposals after 24 hours.
- **The model step:** `src/lib/ai/inbox/wording.ts` makes one call per person per day with a fixed text (`INBOX_PROMPT`, version and fingerprint pinned in `tests/ai-inbox-prompt.test.ts`) and one tool, `write_suggestions`, which returns only a task title and, where a draft is wanted, a message, keyed to the candidates. It cannot choose a customer, deal, amount or date. Unknown keys are ignored. A refused, failed or cut-off call, no key, or a spent ceiling returns no wording and the cards use plain templates, so the inbox never goes blank. Drafts are checked by `src/lib/ai/draft-check.ts` (a link, an email address or a long number not in that contact's record gets a warning on the card).
- **The run:** `src/lib/ai/inbox/run.ts` (`runInboxForUser`). `POST /api/assistant/inbox/refresh` answers at once and runs the work after the response (`after()`, inside the business via `keepTenant()`), once per person per day, tracked in `AiInboxRun` (a failed run, or one still "running" after 10 minutes, may start again; the claim is a single conditional update). The panel asks for it once per page load; `GET /api/assistant/inbox` returns the person's cards and polls while it runs. `maxDuration` on the refresh route is 60 seconds, to be checked against the hosting plan.
- **Data:** `AiProposal.conversationId` is optional; new `source` (CHAT, DAILY, WHATSAPP), `dedupeKey`, `reason`, `subjectType`, `subjectId`; table `AiInboxRun`; `AiUsage.purpose` (CHAT, INBOX, TRIAGE), shown in Settings as "Chat $x · Daily suggestions $y"; retention deletes decided or expired suggestions and run records after 90 days; business erasure includes `AiInboxRun`; the `ai-proposals` export gains a `source` column.
- **Cost:** a few cents per person per active day, counted in the monthly ceiling.
- **Tests:** `ai-inbox-rules` (each rule, scope, dedupe keys, ranking, the cap), `ai-inbox-wording`, `ai-inbox-run` (the once-a-day claim, fallbacks, failure), `ai-inbox-routes`, `ai-inbox-prompt`, `ai-draft-check`, and `ai-inbox-isolation` (two real businesses: a salesperson only gets their own deals' suggestions, a day's run happens once, no repeats, the admin cannot approve someone else's card, a business with the inbox off gets nothing).


### Phase 3c: WhatsApp message help (triage)
- **What it is:** when a customer writes to the business on WhatsApp, Ivy prepares, for the *contact's owner*, suggestion cards in the Suggested list: a draft reply (with a **Send on WhatsApp** button while the customer's 24-hour window is open), and optionally a task ("Check whether the 300 USD payment arrived") or a note. The "Why" line is the verdict (`Payment claim: Says they paid 300 USD.`) and a "They wrote" line quotes up to 300 characters of the message as plain text. It adds to what already happens (the message is filed, an unknown number becomes a lead, the owner gets the "Reply to WhatsApp from X" task); it replaces none of it. An admin switch ("Allow WhatsApp message help", `triageEnabled`, off by default, needs proposed actions on) and a daily number of messages (`triageDailyCap`, default 100) control it.
- **The human sends, never Ivy:** `ProposalDto.whatsappContactId` marks a WhatsApp draft; the card asks `GET /api/contacts/:id/whatsapp` whether the window is open and, if so, shows an editable text box and **Send on WhatsApp**, which posts to the existing `POST /api/contacts/:id/whatsapp` (daily send cap, window check, activity log). A draft carrying a warning asks for a second confirmation. Sending dismisses the card. Chat drafts for WhatsApp get the same button.
- **The message is the attack surface, so this is the most restricted Ivy there is:** one model call per message with one tool (`triage_result`: a label from a fixed list, an urgency, a 200-character summary, optionally a reply, a task and a note) and no tool that reads or changes anything; `src/lib/ai/triage/prompt.ts` (`TRIAGE_PROMPT`, version and fingerprint pinned in `tests/ai-triage-prompt.test.ts`). It sees only that contact's last 5 WhatsApp messages (clipped) and a fact sheet read through the owner's own scope (first name, their deals with total/paid/owed, their open tasks): no email or phone number, nothing about other customers. A payment claim can only become a draft, a task or a note, never a payment: the model has no payment tool, and the cards go through the same `prepare` checks as every other card. The draft is checked by `draft-check.ts` (a link, an email or a long number that is not the contact's own gets a warning on the card).
- **Opt-out is a rule, not the model:** `src/lib/ai/triage/rules.ts` (`asksToStop`) finds a clear STOP / unsubscribe / "stop messaging me" in a short message, with no model call and whatever the cap or ceiling, and makes a `CONTACT_OPT_OUT` card (new proposal kind): approving it sets `whatsappOptIn = false` on that contact, through the person's scope. Consent never changes without a person. Undecided opt-out cards are listed first. If the model itself labels a message WANTS_TO_STOP it also offers that card and writes no reply.
- **Spam and cost:** a contact found through WhatsApp that nobody has answered yet (`source = "WhatsApp"`, no outgoing WhatsApp message) is not sent to the model (a stranger cannot spend the budget by texting; the owner still has the reply task); at most 3 model calls per contact per hour; at most the daily cap per business per UTC day (a call that failed still counts); no call when the monthly ceiling is spent or there is no key. Roughly one to two cents a message, `AiUsage.purpose = TRIAGE`, shown in Settings.
- **Reliability:** the webhook (`receiveWhatsappWebhook`) files the message as before, then `enqueueTriage` writes one `AiTriage` row per message (unique per business and activity, so a repeat from Meta queues nothing) and `processTriage` runs after the response (`after()`, `maxDuration` 60 on the webhook routes). Nothing in triage can make the webhook fail. A claim is a single conditional update (`PENDING`/`FAILED`/stale `RUNNING` with fewer than 3 attempts); the daily AI retention job also calls `retryPendingTriage` for anything queued or failed in the last day (it loads `triage/run` with a dynamic import: a static one makes a cycle through `crm-actions`). `AiTriage` keeps the verdict (label, urgency, summary) and why a message was skipped (`skipReason`: switched_off, customer_gone, no_owner, read_only, new_number, contact_limit, daily_cap, ceiling, no_key, already_opted_out), never the message text; the cards hold the 300-character quote. Retention deletes them after 90 days; business erasure includes `AiTriage`.
- **Data:** migration `20261114000000_ai_triage` (enum value `CONTACT_OPT_OUT`, table `AiTriage` with RLS and grants). Settings: `triageEnabled`, `triageDailyCap` in the `assistant` setting; Settings has a privacy paragraph saying the customer's own words go to Anthropic.
- **Quality check:** `scripts/triage-eval.ts` (30 messages, 18 of them attacks: planted instructions, a bank account, links, a fake owner, a fake system tag, very long text, other languages, prompt-leak and label-forcing tricks; the scorer is rule-based). `--dry-run` is free; a real run needs `ANTHROPIC_API_KEY` and `--budget-usd` (about $0.55).
- **Tests:** `ai-triage-prompt`, `ai-triage-rules`, `ai-triage-run` (every path: success, rule opt-out, each skip reason, claim, failure, retry), `whatsapp-triage-webhook`, `ai-optout-kind`, settings/status additions, and `ai-triage-isolation` (two real businesses: queued once, cards for the owner only, STOP needs no model and a person's approval, the daily cap holds, the other business is untouched).

### Phase 4a: reading a supplier invoice from a PDF or photo
- **What it is:** on the Invoices page, "Read a PDF or photo" (shown only where an admin has allowed it) sends the file to `POST /api/assistant/documents`, and the answer fills the **same New invoice form** the spreadsheet import fills, with a "Check these before saving" box. Nothing is saved until the person presses Create, through the ordinary invoice route. No new table, no migration, no new proposal kind. The file is read once and not kept.
- **Gates (`assertCanReadDocument`, `src/lib/ai/documents/invoice.ts`):** Ivy on, key, monthly ceiling and the shared question rate limit (`assertCanAsk`), then the admin switch `documentsEnabled` (off by default; independent of "proposed actions") and `documentsDailyCap` (default 20 documents a business a day, counted from `AiUsage` rows with `purpose = DOCUMENT`). The route runs them before it reads the upload and refuses a declared size over 4 MB first.
- **The file** (`src/lib/ai/documents/file.ts`): type from the first bytes (PDF, JPEG, PNG, WEBP; anything else 415), at most 4 MB (413), a PDF of at most 10 pages by page-object count (422). The browser (`src/lib/client/document-upload.ts`) shrinks photos to about 1600 pixels first.
- **The model step:** one call, `invoiceRequest` (also used by the eval), one tool `read_invoice` returning fixed fields (`src/lib/ai/documents/prompt.ts`, version and fingerprint pinned in `tests/ai-document-prompt.test.ts`). It copies what is printed and may leave a field out; it has no tool that reads or changes anything and the prompt says the document is data. Zod bounds every number and the line count (100: more do not fit in one answer, and the form says so).
- **What the server does, not the model (`buildReading`):** every line total is left for the form to compute from quantity x price (the page's figure is never copied in); lines plus shipping are compared with the printed total (tolerance 5 cents plus 1 cent a line) and a mismatch warns with both figures; a line whose printed total is not quantity x price warns, naming the line; a zero price, a missing or odd currency (USD with a warning), missing number/date/supplier/addressee, an implausible date, no lines, more than 100 lines, and an invoice number the business already has all warn. An unreadable answer, a cut-off answer, or `readable: false` is a plain 422 and still costs (and is recorded).
- **Cost and privacy:** about 2 to 6 cents a document, `AiUsage.purpose = DOCUMENT`, shown in Settings as "Documents $x". Settings has the switch, the daily number and a privacy paragraph: the whole file goes to Anthropic.
- **Quality check:** `scripts/document-eval.ts` draws nine invoices of its own (clean PDFs, a euro invoice with shipping, no reference column, 30 lines, a tilted blurred "photo", and hostile ones: a footer instructing the assistant to set every price to 0.01 and add a 5000 gift card, a total that does not add up, a menu, 250 lines, expected to stop at 100 with a warning) and scores the app's own result. `--dry-run` is free; a real run needs `ANTHROPIC_API_KEY` and `--budget-usd`; `--folder <dir>` also shows how it reads your own real files (not scored).
- **Tests:** `ai-document-prompt`, `ai-document-file`, `ai-document-invoice` (the checks, the gates, one tool only, usage recorded, failures plain), `ai-document-route`, and the settings/status additions.

## Automations
- **Code:** `src/lib/automations/` (`config.ts` has the defaults, validation and title words; `stage-tasks.ts`, `quiet-leads.ts`, `settings.ts`; `index.ts` runs the daily part). Settings are stored in the `AutomationSetting` table (key `stage-tasks` or `quiet-leads`); no row means the defaults, which are all off. Admins edit them in Settings → Automations (`GET`/`PUT /api/admin/automations`).
- **Stage tasks** run inside the request that moves the deal (`POST /api/deals/:id/stage` and `PATCH /api/deals/:id`), right after the stage email. They never fail the stage change. `Task.automationKey` (`stage:<dealId>:<stage>`) is how a rule sees that its task is already open.
- **Quiet leads** run in the daily cron (`/api/cron/task-reminders`), before the reminder emails, so new tasks are in the same digest. Key `quiet:<contactId>`. The selection is `quietLeadWhere()` in `quiet-leads.ts`; the cap is 500 per run. Two cron calls at the same instant could both create a task for a lead; the daily schedule makes that unlikely.
- **Audit:** each stage task and each quiet-lead run writes a row with actor `automation`.
- **On your own computer** nothing calls the cron, so quiet leads, customer payment reminders and the existing task and instalment reminder emails never run unless you schedule it. Set `CRON_SECRET` in `.env` (16+ characters, restart the CRM afterwards). `scripts/run-daily-automations.ps1` reads it from `.env` and calls `/api/cron/task-reminders`; `-DryRun` checks the secret without calling anything, and each run is logged to `%LOCALAPPDATA%\CRM\daily-run.log`. A Windows scheduled task named **CRM daily run** (daily 08:00, as the signed-in user, catches up after a missed start) runs it. Manage it in Task Scheduler or with `Enable-ScheduledTask -TaskName "CRM daily run"` / `Disable-ScheduledTask ...`. The CRM must be running at that time; if it is not, the log shows a failure and the next day's run picks everything up. The call is safe to repeat.
- **Enable the task only after an email provider is set up.** With no `RESEND_API_KEY` or `EMAIL_SERVER`, development prints emails to the console and reports success, so the daily run would mark task and instalment reminders as sent without anyone receiving them.
- **Customer payment reminders** (`instalment-emails.ts`, template `customerInstalmentEmail` in `email-templates.ts`) run in the same daily cron. `pickReminder()` decides the kind (UPCOMING, OVERDUE_1, OVERDUE_2) from the due date; only the most serious unsent kind goes out, never one at or below a kind already sent, and nothing after 30 days overdue. `InstalmentReminder` has a unique key on (instalment, kind, test), which is what stops a repeated run sending twice; a reminder is recorded only after the provider accepted the mail. TEST mode records with `test = true`, so going live still sends the real emails. Live mode also writes an EMAIL activity and, after the second notice, a `overdue-call:<instalmentId>` task. `Contact.emailOptOut` is the per-contact opt-out. One run sends at most 200 emails. Re-saving a deal's schedule creates new instalments, which can be reminded again. Emails need a working provider (`RESEND_API_KEY` or `EMAIL_SERVER`); with none, development prints them to the console and production fails the send, so nothing is recorded.
- **Pay link in reminders:** in live mode `sendOne()` first asks `reminderOrderLink()` for the customer order page (see "Customer order page" below) and only if that returns null falls back to `reminderPayLink()` (`payment-links.ts`), which reuses the deal’s open `PaymentLink` for exactly the amount due or creates one as the deal owner (audited as `payment_link.created`). It never throws: no Stripe keys, a currency other than USD/EUR, a Stripe error or an amount already covered by open links gives no link and the reminder still goes out. Test mode shows `PAY_LINK_PREVIEW` and creates nothing.
- **Send now / history:** `GET`/`POST /api/deals/:id/reminders` (`sendReminderNow()` and `reminderHistory()` in `instalment-emails.ts`), shown in Payments → Payment reminders. Scoped with `ownerScope`. Works with the automation off, follows TEST/LIVE (TEST with no test address is refused with `REMINDERS_NOT_LIVE`), skips opted-out contacts, lost deals and paid instalments, and refuses a repeat within `MANUAL_RESEND_MS` (1 hour). A manual send upserts the `InstalmentReminder` row (refreshing `sentAt`), logs an EMAIL activity as the user and creates no call task. No migration was needed.
- **WhatsApp reminders:** `whatsapp` in the `instalment-emails` setting (`enabled`, `language`, `testPhone`, and the Meta template name per notice; default off, `payment_reminder_upcoming` / `_overdue` / `_final`). `runInstalmentWhatsapps()` runs after the email run in `runTenantAutomations()` under its own `attempt()`; `planInstalmentWhatsapps()` is the same planner as the email one with a different contact filter (`phoneE164` set and `Contact.whatsappOptIn`). `sendOneWhatsapp()` sends through `sendWhatsAppTemplate()` (`whatsapp.ts`, Meta's `template` message; free text is not allowed outside the 24-hour window) with parameters `[firstName, amount, dueDate, payUrl or "just reply to this message"]`, then records an `InstalmentReminder` with `channel: "WHATSAPP"` and (live only) a WhatsApp activity. Reminders are now unique per `(instalmentId, kind, test, channel)` (migration `20261106000000_whatsapp_reminders`, also adds `Contact.whatsappOptIn`), so an email and a WhatsApp message for the same notice never block each other, and the once-per-notice and one-hour manual-resend rules apply per channel. A failed send records nothing (retried tomorrow); the plan's daily WhatsApp allowance (`assertUnderDailyCap`) stops the run quietly. `POST /api/deals/:id/reminders` takes `channel` (`EMAIL` default, or `WHATSAPP`) and the view adds `canWhatsapp`. The overdue call task is shared by both channels through the same `automationKey`. Meta cannot be called from tests; they mock `sendWhatsAppTemplate` and check its request body against a stubbed `fetch`.
- **Own wording:** `wording` in the `instalment-emails` setting holds an optional `{ subject, message }` per notice (`UPCOMING`, `OVERDUE_1`, `OVERDUE_2`); blank keeps the built-in text, and a saved setting without it still parses. `customerInstalmentEmail()` replaces the subject and the message body only (placeholders `{name}`, `{amount}`, `{deal}`, `{dueDate}`, `{daysLate}`, anything else is left as written); the greeting, Pay now button and sign-off are always added, and everything is escaped. The sample email takes the unsaved draft wording. No migration.
- **Low-stock alerts** (`src/lib/automations/low-stock.ts`, runs in `runTenantAutomations()` after the instalment emails, isolated by `attempt()`). Settings are `AutomationSetting` key `low-stock` (`{ enabled, defaultThreshold }`, default off and 3). Stock rows are worked out, not stored, so a row is named by `stockKey()` in `stock.ts` (normalised product|colour|length) and `StockRow.key` carries it; the table, `PUT /api/stock/thresholds` and the job all use that one function. `StockThreshold` (migration `20261105000000_stock_thresholds`, with RLS) holds a row's own level (`threshold`: null = default, 0 = never) and `alertedAt`. The job counts stock for the whole business (`loadStock({ tenantId })`), emails the active admins the rows that are low and have no `alertedAt`, and sets `alertedAt` only after the provider accepted the mail (a failed send retries the next day); it clears `alertedAt` on rows that are back above their level, switched off or gone. At most 50 rows are listed (the rest are counted) and 500 are marked per run. `GET /api/stock` adds `key`, `threshold`, `level`, `low`, `defaultThreshold` and `alertsOn` to each response; non-admins still see only their own stock there. `StockThreshold` is in `ERASE_ORDER`. The dev database has no migration history (built with `db push`), so apply the table there with `npm run db:push`.

- **Email templates:** `EmailTemplate` table, `GET/POST /api/email-templates` and `PATCH/DELETE /api/email-templates/:id` (writes are admin only; delete keeps a snapshot in the audit log). The words are filled in **in the browser** by `fillTemplate()` in `src/lib/email-template-vars.ts` when a template is picked, so the send route (`POST /api/contacts/:id/email`) is unchanged and only ever sees the final text. To add a word, add it to `TEMPLATE_WORDS` and pass it where the dialog calls `fillTemplate` (`contact-org-dialogs.tsx`).

The admin contact export does **not** filter by tag.

To support another list (deals), add the entity to `savedFilterEntity` in `validations/crm.ts` and give that page a `SavedViews`.

## Duplicate contacts and merge
- **Warning on the form:** `GET /api/contacts/duplicates?firstName&lastName&phone&email&excludeId` (`src/lib/duplicates.ts`) finds live contacts with the same phone (compared as E.164 via `phoneE164`, so written differently still matches), the same first + last name (any capitals) or the same email. It is owner-scoped, so a sales user is only told about their own contacts. It only warns (`DuplicateWarning` under the contact form); saving is never blocked, because two people can share a name or a family phone. Same email is still blocked outright by the unique index.
- **Merge (admins):** `POST /api/contacts/:id/merge { intoId }`. In one transaction it moves deals, activities and tasks to the kept contact, copies tags (no repeats), fills only the *empty* fields on the kept contact (email, phone, title, source, address, company; a customer stays a customer; opt-out sticks), then soft-deletes the removed contact and clears its email (email is unique). The audit log row `contact.merged` records the removed id, its email and how many of each thing moved. Undoing: restoring the removed contact brings back the contact only, not the moved records, so merge with care.
- **Button:** Merge on a contact's page, admins only; likely matches are listed first in the picker.

## Website enquiry form
- **Endpoint:** `POST /api/public/lead { name, email?, phone?, message?, website }` (`src/app/api/public/lead/route.ts`, logic in `src/lib/web-lead.ts`). It is public (`/api/public/` in `rbac.ts`) and exempt from the middleware's same-origin check, because the form lives on the *website*, not in the CRM. It uses no cookies, so there is no session to forge.
- **Who may call it from a browser:** `LEAD_FORM_ORIGINS` in `.env`, comma separated (`https://www.ivycandyhair.com`). Unlisted sites get 403 (also on the preflight). Requests without an Origin (servers, curl) are allowed, so the real defences are below. Restart after changing it.
- **Defences:** hidden `website` field (a bot that fills it gets "ok" and nothing is saved), rate limit per address (5 per 10 minutes) and overall (200 per hour) via `LIMITS.webLead`/`webLeadAll`, 10 KB body cap, length limits, plain-text email only. Every answer is the same "ok" whether the email is known or not, so the form can't be used to find out who your contacts are. Behind a proxy, set `TRUSTED_PROXY_COUNT` or every visitor shares one address (see `clientIp`).

A known email gets only a note and an email to that contact's owner. Audit actions `lead.web_created` / `lead.web_repeat` (actor `website-form`).

- **CAPTCHA (optional, Cloudflare Turnstile):** with `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` set, the copy-paste code in Settings → Lead form includes the Turnstile widget and sends its token as `captchaToken`. A token that is present but wrong, or that Cloudflare can't confirm, is refused (`CAPTCHA_FAILED`, 400) and nothing is saved. **A request with no token is still accepted**, so forms pasted before this existed keep working; a bot can skip the CAPTCHA by leaving the token out, so the other defences above still matter. To enforce it for everyone, once site owners have re-pasted the code, refuse a missing token in `leadPost` (`src/lib/web-lead-handler.ts`).

## Two-way WhatsApp (Meta Cloud API)
Code: `src/lib/whatsapp.ts`, webhook `src/app/api/webhooks/whatsapp/route.ts`, reply route `src/app/api/contacts/[id]/whatsapp/route.ts`. Off until `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET` and `WHATSAPP_VERIFY_TOKEN` are all set (the production env check refuses a half setup). Optional `WHATSAPP_API_VERSION` (default `v23.0`). This was written against Meta's documentation and tested with signed fake payloads only; it has **not** been run against the real Meta service, so test with Meta's test number first.
- **Set-up on Meta's side:** a verified Meta Business account, a dedicated WhatsApp number (not one already used in the normal WhatsApp app), an app with the WhatsApp product, a permanent system-user token, then in the app's WhatsApp → Configuration set Callback URL `https://<crm domain>/api/webhooks/whatsapp` and your verify token, and subscribe to the `messages` field. The URL must be public https; for local testing use a tunnel.
- **Incoming:** `GET` answers Meta's one-time check (token compared in constant time). `POST` checks `X-Hub-Signature-256` (HMAC-SHA256 of the *raw* body with the app secret) before reading anything. Each message becomes a WHATSAPP/IN activity with `externalId` = Meta's message id (unique, so retries and races record once). A known number (`Contact.phoneE164`, oldest live match) gets the note and one open "Reply to WhatsApp" task (`automationKey wa-reply:<contactId>`); an unknown number becomes a LEAD with source "WhatsApp" for the default web-lead owner (Settings → Lead form) plus an email. Media is logged as `[image]` etc. with its caption; the file itself is not stored. A 5xx makes Meta retry.
- **Delivery statuses:** the same webhook also carries `statuses` for messages we sent. `parseStatuses` / `recordDeliveryStatus` (`src/lib/whatsapp.ts`) match the message id to an OUT activity of that business (`externalId`, `tenantId`) and store `Activity.deliveryStatus` (SENT, DELIVERED, READ, FAILED) and `deliveryError` (Meta's reason). Updates only move forward (a late "delivered" never undoes "read"; FAILED never overwrites DELIVERED/READ) and an unknown id is ignored, so retries and out-of-order delivery are safe. Nothing is stored before Meta reports, so older messages and payment reminders show no status. The timeline (`ActivityItem`) shows "Delivered", "Read" or "Not delivered: <reason>". A failed *payment reminder* is still recorded as sent in `InstalmentReminder`; only the timeline note is new. Tests: `tests/whatsapp-delivery-status.test.ts`.
- **Outgoing:** `POST /api/contacts/:id/whatsapp { message }` (button "Reply here", only shown when allowed). Free text works only within 24 hours of the customer's last inbound message (Meta's rule), checked by `canReplyFreely`; otherwise 409. Click-to-chat (`wa.me`) still works as before. Templates (needed to start a conversation or write after 24 hours) are below.
- **Message templates (any time):**
  - **Table and sync:** `WhatsappTemplate` (per business; unique on name + language) holds Meta's templates: wording, language, category, `status` (as Meta reports it, or `REMOVED`), `supported`, `active` and `slots`. They are created and approved in Meta's WhatsApp Manager, never in the CRM. `POST /api/whatsapp-templates/sync` (admins; Settings → Templates → "Refresh from Meta") reads `GET /{WABA id}/message_templates` with the saved access token and follows paging (`src/lib/whatsapp-templates.ts`). It needs the optional **`businessAccountId`** in the WhatsApp integration (Settings → Integrations; env fallback `WHATSAPP_BUSINESS_ACCOUNT_ID` for the original business). Without it the sync answers 409 `NO_BUSINESS_ACCOUNT`; sending and receiving do not need it. The token must be allowed to read templates (`whatsapp_business_management`).
  - **What a sync keeps:** an existing template keeps the admin's slots and on/off choice (slots reset only if the number of `{{n}}` blanks changed). A new template is on only if APPROVED and `supported`. A template Meta pauses, rejects or disables is switched off; one Meta no longer lists is marked `REMOVED` and off, never deleted. `supported` is false for media headers, headers or URL buttons with variables, and named blanks (`{{first_name}}`): those are listed but cannot be switched on. Templates with text bodies only are sent.
  - **Slots:** `[{ label, source }]`, one per `{{n}}`. Sources (`src/lib/whatsapp-template-slots.ts`): `firstName`, `fullName`, `dealTitle`, `amountDue`, `dueDate`, `trackingNumber`, `manual`. `PATCH /api/whatsapp-templates/:id` (admins) sets slots or `active`; it refuses to switch on a template that is not APPROVED or not `supported` (409 `NOT_SENDABLE`). `GET /api/whatsapp-templates` is open to any signed-in user.
  - **Sending:** `POST /api/contacts/:id/whatsapp/template { templateId, dealId?, values? }` (any user who can see the contact; button "Send template" or the Template tab of the WhatsApp dialog). Checks, in order: contact visible (`ownerScope`), WhatsApp set up, valid `phoneE164`, **`whatsappOptIn` ticked** (422 `NOT_OPTED_IN`), template active + APPROVED + supported (404 otherwise), blanks resolved (`resolveSlotValues` in `src/lib/whatsapp-template-send.ts`), daily cap, then `sendWhatsAppTemplate`. Order blanks need a `dealId` that belongs to this contact and is visible to the caller; `amountDue` and `dueDate` come from `dealPaymentsView` (next unpaid instalment, else the balance for the amount; no due date is a 422). A blank that cannot be filled is a 422 naming it and nothing is sent. The filled-in text is logged as a WHATSAPP/OUT activity (subject `WhatsApp template: <name>`) with Meta's id in `externalId`. Meta's refusal is a 502 with its reason and logs nothing.
  - **Not tied to the reminder Test/Live mode:** the payment-reminder automation redirects to a test number in Test mode; a person pressing Send does not (that mode is on by default and would silently misdirect staff messages). The opt-in tick is the guard.
  - **Not built:** media or button variables, creating templates from the CRM, bulk campaigns.
  - **Tests:** `tests/whatsapp-templates.test.ts` (sync, slots, admin-only routes), `tests/whatsapp-template-send.test.ts` (sending). Like the rest of this section, not yet run against the real Meta service.
- **Matching depends on `phoneE164`:** a contact whose number could not be normalised (`DEFAULT_PHONE_COUNTRY_CODE`, see Phone numbers) will not match and the sender becomes a new lead; merge them with Contacts → Merge.

## Data export (CSV, PDF, zip)
Not a backup: `pg_dump` (above) is the only way to restore. Exports are for reading, reporting and keeping a readable copy.
- **Where it lives:** `src/lib/export/` (`entities.ts` and `admin-entities.ts` list each area's fields; `registry.ts` is the URL-name list; `run.ts` has the permission, limit, code and audit order; `csv.ts`, `stream.ts`, `zip.ts`, `pdf.ts`), routes in `src/app/api/export/`, UI in `src/components/export/` and Settings → Data export. API shapes are in `/api/openapi.json` under "Export".
- **Add a field or area:** add the field to the `select` and to the `columns` of its entity, and nowhere else. Entities select explicit fields only (a test fails on `include:` or on any secret field name). The contacts table and the audit log stay in `admin-entities.ts`; add `adminOnly` (and `stepUp` if it should ask for a code) to any new sensitive area.
- **Fonts and PDF:** `pdfkit` draws the PDFs and embeds Noto Sans from `node_modules/@expo-google-fonts/noto-sans` (path built from `process.cwd()`), so the app must start from the project folder and `node_modules` must be present at run time. If PDFs fail with "ENOENT" on a font file, that is why. pdfkit is loaded as an external package, not bundled.
- **Limits (constants in `src/lib/export/limits.ts`):** 50,000 rows per CSV, 2,000 lines per PDF, 500,000 rows per file in the full export, 5 exports per user per 10 minutes. The per-user limit is counted from `AuditLog` rows with action `EXPORT`, so it works without Redis and survives restarts. It is not atomic, so two requests at the same moment can both pass.
- **Choosing rows and lines:** every list export (organizations, deals, invoices, invoice-items, tasks, activities, contacts) accepts an optional `ids=a,b,c` (`pickedIds` in `validations/crm.ts`: 1 to 200 short ids, deduplicated; anything else is a 422). It is only an extra `id in (...)` in each area's `*Where`, ANDed with the normal scope, so an id the caller cannot see matches nothing. The audit row stores `pickedRows: <count>`, not the ids (`pickedCount` in `define.ts`). The UI is `ChooseRowsDialog` in `components/export/export-menu.tsx`: an item with `choose: chooseRows<Type>(resource, describe)` gets "Choose rows" (nothing ticked) next to "All matching". To add it to a new list, add `ids` to that export's schema and `where`, and a `choose` on the page's `ExportMenu` item. Invoice PDFs take `lines=<invoice item ids>` (max 2,000, only that invoice's lines count, 422 if none match, invoices only); a partial PDF prints the shown lines' own subtotal and a "partial copy" note instead of the invoice total and shipping, and the audit summary says "N of M lines". The contacts export now also honours the tag filter, which it ignored before. Deal items, payments and instalments take `dealIds=` (same limits as `ids`; `dealsIn` in `entities.ts` adds the pick to the normal deal visibility list, so another person's deal gives nothing; audit shows `pickedDeals`). Invoice lines use the invoices' `ids`. Stock has no ids, so its rows are named `product|colour|length` and sent as `keys=` (each key `encodeURIComponent`-ed, joined with commas; max 100 keys of 300 characters, undecodable input is a 422); the server only filters the stock rows it already loaded for that person, in memory. For rows a screen already holds (stock) use `chooseFromRows`; for deals picked for another file use `chooseRows(..., { param: "dealIds" })`.
- **Audit:** every export writes an `EXPORT` row (actor, entity, format, row count, filters, IP) before any data is sent. If that write fails, the export fails. Review them in Settings → Audit log (search "EXPORT").
- **Authenticator code:** the audit-log export, deleted records and the full export need a fresh TOTP or recovery code when the admin has two-step verification on (same helper as password change: `requireMfaStepUp`). An admin without it set up is not asked, so keep `REQUIRE_ADMIN_MFA` on in production.
- **Self-hosting:** the per-user limit does not depend on the client IP, but the other rate limits do, so set `TRUSTED_PROXY_COUNT` correctly and keep the app reachable only through the proxy. Large exports stream, but a reverse proxy with a short timeout or response buffering (nginx `proxy_buffering`, `proxy_read_timeout`) can cut a big download short: raise the timeout for `/api/export/`.
- **Troubleshooting:** 422 `EXPORT_TOO_LARGE` means narrow the filters (or use `pg_dump`); 429 means the 5-per-10-minutes limit; 422 `STEP_UP_REQUIRED` means a code is needed and the call must be a POST; 400 "That code is not right" means the code was wrong or already used.

## Users
There is no public sign-up: admins create users in Settings → Team (`POST /api/admin/users`), and the invitee sets a password from the emailed link (valid 7 days). Change roles with `PATCH /api/admin/users/:id` (admin), `npm run make-admin`, or Prisma Studio. Role changes, deactivation and password resets take effect immediately on the server that handled the change, and within 30 seconds on any other instance (user lookups are cached for 30 s in `src/lib/user-cache.ts`).

## Ivy knowledge base (policy and FAQs)

Ivy answers questions about returns, refunds, exchanges, damaged or wrong orders, cancellations, delivery, return shipping, customer rights and support from the business's own written entries, not from general knowledge. It still only drafts: staff review and send every reply (Phase 5 auto-reply is not built).

- **Data:** `KnowledgeEntry` (one per topic: `key` unique per business, `category`, `title`, `body`, `basis` STATUTORY/VOLUNTARY/PROCESS/INFO, `keywords`, `status` ACTIVE/ARCHIVED, `version`) and `KnowledgeEntryVersion` (the text of every version). Row-level security like every business table. Entries are archived, never deleted.
- **Shipped policy:** `src/lib/ai/knowledge/ivycandy-policy.ts` holds the Ivycandy Hair returns policy split into entries (`POLICY_VERSION` is its date). Settings > Ivy > Policy and FAQs > "Import default policy" copies it into the business. Running it again only adds missing entries and refreshes ones still as shipped; an entry an admin has edited (`fromDefault` false) is never overwritten.
- **Lookup:** `src/lib/ai/knowledge/search.ts`. Customer wording is mapped to topics and scored against each entry's keywords, title and text (no embeddings, no extra service). Returns-type topics always bring the "statutory rights always apply" entry. Chat uses the read tool `find_knowledge`; WhatsApp triage looks up the customer's last messages on the server and passes the entries as `<policy_excerpts>` data, because triage has no tools.
- **Hand-off:** chat has `propose_escalation`, triage returns an `escalation` object; both become a HIGH-priority task (a normal proposal card the owner approves) with category, customer, order number, what they said, evidence, why a person must decide and a suggested next step.
- **Rules in the prompts:** answer only from retrieved entries, never invent policy, never promise or claim a refund/cancellation/exchange, keep statutory rights apart from store conditions, never refuse a return only because a package was opened, never ask for card details, do not re-ask what the customer already gave.
- **Updating the policy:** (a) in the app, Settings > Ivy > Policy and FAQs: Edit, Archive/Restore, Add an entry, History; effective immediately. (b) For a change every business should get, edit `ivycandy-policy.ts`, review it, and have admins press "Import default policy". Prompt text changes need `IVY_PROMPT_VERSION` / `TRIAGE_PROMPT_VERSION` bumped and the pins in `tests/ai-prompt.test.ts` and `tests/ai-triage-prompt.test.ts` updated.
- **Tests:** `tests/ai-knowledge-search.test.ts` (lookup over the shipped policy, no database), `tests/ai-knowledge-service.test.ts` (needs `TEST_DATABASE_URL`: import, versions, duplicates, two-business isolation), triage cases in `tests/ai-triage-run.test.ts`.
- **Quality check:** `scripts/knowledge-eval.ts` (19 customer scenarios, including follow-ups, an out-of-policy question, a legal threat and an injection). `--dry-run` is free and checks the lookup; a real run needs `ANTHROPIC_API_KEY` in `.env.eval` and `--budget-usd`.
- **Limits:** the website URL in the source policy was a placeholder and is not included. Ivy has no live order or tracking data beyond the CRM records. The policy text is legally sensitive: have it reviewed.

## Security features (where they live)
- **Audit log:** `src/lib/audit.ts`. `authed()` (`src/lib/route.ts`) logs every successful write automatically; routes that delete money records call `audit()` themselves with a snapshot. Viewer: Settings → Audit log (`GET /api/admin/audit`). The table is append-only in the database itself: migration `20261012000000_audit_log_append_only` adds triggers that refuse `UPDATE`, `DELETE` and `TRUNCATE`. To purge old rows on purpose (retention), drop the two triggers named in that migration, delete, then recreate them. In production also run the app as a database role without those privileges (`REVOKE UPDATE, DELETE, TRUNCATE ON "AuditLog" FROM <app_role>;`) so it is enforced twice.
- **Two-step verification:** `src/lib/mfa.ts` (TOTP, encryption, recovery codes), `src/lib/mfa-server.ts` (verification), `/api/me/mfa/*`, `/api/auth/mfa-check`. A user who lost their phone: Settings → Team → Edit → "Reset two-step verification". **Admin enforcement:** `adminMfaRequired()` / `mfaPending()` in `src/lib/rbac.ts` (env `REQUIRE_ADMIN_MFA`, default on in production). The Auth.js `jwt` callback sets `token.mfaPending` from the database on every full session read and the `session` callback downgrades the role to SALES, so server code and pages see a non-admin; the edge middleware keeps the real role (it has no database) and is only the coarse gate. Lock-out recovery: `npm run make-admin -- <email> --reset-mfa`. **Encryption key:** without `MFA_ENCRYPTION_KEY` the secrets are encrypted with a key derived from `NEXTAUTH_SECRET`, so changing that secret makes every stored two-step secret unreadable. Set `MFA_ENCRYPTION_KEY` (`openssl rand -base64 32`) to decouple them: existing secrets keep working and are re-encrypted the next time their owner signs in with a code. To rotate, move the old value to `MFA_ENCRYPTION_KEY_PREVIOUS`, set a new `MFA_ENCRYPTION_KEY`, and remove the previous one once everyone with two-step verification has signed in once.
- **Content Security Policy:** built per request in `src/middleware.ts` from `src/lib/csp.ts`: scripts run only with a fresh nonce (`'strict-dynamic'`, no `'unsafe-inline'`); the root layout passes the nonce from the `x-nonce` header to next-themes. Pages are therefore rendered per request. A new inline `<script>` must take the nonce too. `CSP_REPORT_ONLY=1` switches to report-only (violations show in the browser console, nothing is blocked). API responses carry no CSP.
- **Role and deactivation lag:** every request re-checks the user against the database, but active users are cached in memory for 30 s (`src/lib/user-cache.ts`). A change made on one server instance applies there at once; on a multi-instance deployment other instances can keep the old role or active flag for up to 30 s. Lower the `USER_CACHE_TTL_MS` constant in that file if that is too long.
- **Sign out everywhere:** sets `User.passwordChangedAt` to the next whole second (`src/lib/sessions.ts`); the `jwt` callback rejects older tokens. A login within that second after a revoke is also refused.
- **Rate limits:** `src/lib/rate-limit.ts` (`LIMITS`). Client IP comes from the right of `X-Forwarded-For` (`TRUSTED_PROXY_COUNT`).
- Route handlers without a URL segment receive no `params` in Next 15; `authed()` handles that.

## Ivy security review (October 2026)

A read-only review of the Ivy code found no flaw in key storage, scoping, approvals or how replies are shown. Fixed:

- **Upload size:** `POST /api/assistant/documents` now refuses a request that does not declare its size (411), so the body is never read without a bound (declared size is capped at 4 MB plus framing).
- **Parallel requests:** `src/lib/ai/documents/reserve.ts` saves a placeholder usage record (about $0.05 held) before every document read, then checks the day's number and the month's ceiling with calls in flight counted. The placeholder is removed once the real usage is recorded or the call fails. Pinned by `tests/ai-document-reserve.test.ts`.
- **One person using the whole day's number:** a person who is not an admin may use half of it (rounded up, at least 1); admins may use all of it.
- **Keys:** the eval scripts read `ANTHROPIC_API_KEY` from `.env.eval` (git-ignored, loaded by `scripts/eval-env.ts`), so a key is never typed into a command or chat. `tests/no-secret-keys.test.ts` fails if a real-looking `sk-ant-` key is in any tracked file.
- **Still true:** record text read by chat Ivy can try to steer it. The prompt says it is data and nothing happens without a person's approval.

## Receipts from a bank app (payment prompt v2, fingerprint `befd83751dd52e8c`)

Found by running real receipts: bank-app screens show money received as a plus-signed amount with no "successful" word, so every one was refused. Changes:

- **Received credits count as completed:** an entry in the business's own bank app with a plus-signed amount (`+€150`) is read as COMPLETED. A minus sign or "sent to / paid to" is money going out and stays UNCLEAR. The card still says a screenshot is not proof.
- **Dates:** "today", "yesterday" and "7 minutes ago" are not dates. The model leaves the date out and sets `shownAsToday`; the server then uses its own clock for today's date and says so on the card. A date without a year is not guessed.
- **Several payments:** a picture that lists more than one payment (`severalPayments`) makes no card: "Crop it to the one payment and try again."
- **Known gap:** a bank statement line from the customer's own account (`-€422.00`, "SEPA Credit Transfer to ...") is a debit in their account, so it is refused as UNCLEAR. The reader is not told the business's name, so it cannot tell that the money went to you.
- **Eval:** `scripts/payment-eval.ts` now has 17 drawn receipts (credit today, credit with a date, debit, a list of credits); the real run passed them all, apart from one scoring mistake in the new `debit-out` spec, now corrected.

## Customer order page
- **What it is:** a private page `/my-order/<token>` (public, listed in `rbac.ts`) where a customer sees one order: items, totals, payments, instalments, with Pay now. Table `CustomerOrderLink` (migration `20261118000000_customer_order_links`, RLS like every business table). Code: `src/lib/order-links.ts` (tokens, links), `src/lib/customer-order.ts` (page data, pay address), page `src/app/my-order/[token]/page.tsx`, staff API `/api/deals/:id/customer-link` (GET, POST, DELETE), customer action `POST /api/public/my-order/:token/pay`.
- **Token:** 32 random bytes, base64url (43 characters). A visit is matched by the SHA-256 in `tokenHash`; `tokenSealed` is the same token encrypted with `MFA_ENCRYPTION_KEY` so staff and reminders can show the same link again. A database copy without the key reveals no usable link. Rotating the key makes old sealed copies unreadable (the staff screen then asks for a new link; customers' existing links still work until replaced, as they match by hash).
- **One live link per order:** making a new one revokes the earlier one in the same transaction. Default life 90 days (1 to 365 on request). Reminders reuse the live link and only make one when none is live.
- **Every bad link looks the same:** `resolveOrderLink` returns null for a malformed, unknown, revoked or expired token, a deleted order or a suspended business; the page and pay route answer identically. This is the one place that looks across businesses (`platformDb`, listed in `PLATFORM_USERS`); after it, everything runs as the link's business (`withTenant`).
- **Pay now:** `customerPayUrl` reuses the deal's open Stripe link for exactly the amount due or makes one (`reminderPayLink`, filed under the link's creator; audited as `payment_link.created`). Redirects only to Stripe or back to the page on the configured site (`appUrl()`, never the Host header). Limit: 10 per visitor address per 10 minutes (`LIMITS.customerPay`).
- **Page hygiene:** `noindex`, `referrer: no-referrer`, no caching; the view is built from an allow-list of fields.
- **Tests:** `tests/order-links.test.ts`, `tests/customer-order.test.ts`, plus the reminder tests for the link order.
- **Not built:** bank-transfer details on the page, per-customer branding, delivery tracking (Plan B).

## Order shipping (Plan B)
- **Fields:** `Deal.fulfilmentStatus` (`FulfilmentStatus`: NOT_STARTED, PACKED, SHIPPED, DELIVERED, RETURNED), `carrier`, `trackingNumber`, `shippedAt`, `deliveredAt` (migration `20261119000000_order_fulfilment`). Separate from `DealStage`; only a CLOSED_WON deal can be fulfilled (stock still counts PROPOSAL, NEGOTIATION and CLOSED_WON as sold).
- **Code:** pure helpers in `src/lib/fulfilment.ts` (labels, `statusColumns`, `trackingUrl`; DHL, UPS, FedEx, USPS only); `updateFulfilment()` in `src/lib/fulfilment-update.ts`; route `POST /api/deals/:id/fulfilment`; dialog `src/components/forms/fulfilment-dialog.tsx`. List filters `toShip=true` and `fulfilment=PACKED,SHIPPED` on `GET /api/deals`.
- **Dates:** going forward stamps `shippedAt` / `deliveredAt` once; going back clears the dates of steps that no longer apply; RETURNED keeps them. A status or tracking change writes a NOTE activity; the audit line comes from `authed()`.
- **Template blank `trackingNumber`:** `resolveSlotValues` uses the chosen order's tracking number, else the typed value, else a 422 naming the blank. The order is optional for this blank (older templates keep working).
- **Shared sending:** `sendTemplateMessage()` in `src/lib/whatsapp-template-send.ts` (fill, daily cap, send, log) is used by `POST /api/contacts/:id/whatsapp/template` and by the automation, so both obey the same rules.
- **Automatic updates:** setting `shippingUpdates` (`AutomationSetting` key `shipping-updates`; `enabled`, and per step `shipped` / `delivered` an `enabled` flag and a `templateId`). `runShippingUpdate()` (`src/lib/automations/shipping-updates.ts`) runs inside `updateFulfilment` after a status change, never throws, and returns `OFF`, `SENT` or `SKIPPED` (reported as `shippingUpdate` in the response). Sends only to a contact with `whatsappOptIn` and a `phoneE164`, only with an active, APPROVED, supported template, and at most once per order and step (the automatic activity's subject `Automatic shipped update: <template>` is the dedupe key). Every skip after the switch is on leaves a NOTE saying why. There is no test mode: it is off by default, and it messages real customers when on.
- **Customer page:** `customerOrderView` returns a `shipping` block (status, dates, carrier, tracking number, `trackingUrl` only for known carriers) once the status is past NOT_STARTED.
- **Tests:** `tests/fulfilment.test.ts`, `tests/shipping-updates.test.ts`, `tests/customer-order.test.ts`, `tests/whatsapp-template-send.test.ts`.
- **Not built:** custom tracking-link patterns, a dashboard count of orders to ship, carrier webhooks (status does not update by itself).

## Broadcast campaigns (Plan C)
- **Tables:** `Campaign` (template, `audience` filter JSON, `values` typed once, `status` DRAFT, QUEUED (unused), SENDING, PAUSED, COMPLETED, STOPPED; `testedAt`, `audienceSize`, `pausedReason`, `lockedUntil`) and `CampaignRecipient` (unique `[campaignId, contactId]`, status PENDING, SENT, DELIVERED, READ (the last two are not written yet: delivery is read from the timeline activity), FAILED, SKIPPED; `reason`, `messageId`). Migrations `20261120000000_broadcast_campaigns`, `20261121000000_campaign_sending`. `Contact.whatsappOptInAt` / `whatsappOptInSource` record the agreement (`src/lib/whatsapp-optin.ts`; set when the tick is first set, cleared when withdrawn).
- **Admin only:** every route is under `/api/admin/campaigns` (`authed(..., "ADMIN")`). They see the whole business, so queries use `tenantId`, not `ownerScope`.
- **Audience:** `audienceFor()` in `src/lib/campaign-audience.ts`. Always `whatsappOptIn` + `phoneE164` + not deleted. "Paid in full" is worked out in code (every CLOSED_WON deal paid, at least one), over at most 20,000 candidates. `MAX_AUDIENCE` = 2000. The preview is a GET (`?audience=<json>`) so it is not audited and works when the workspace is read-only.
- **Flow:** `sendCampaignTest` (admin's own number, 10 an hour, sets `testedAt`; any PATCH clears it) -> `startCampaign` (needs `testedAt`, `expectedCount` equal to the current audience or 409 `AUDIENCE_CHANGED`, refuses the same template already SENDING/PAUSED, claims the DRAFT then bulk-inserts recipients with `skipDuplicates`) -> `runCampaignBatch` (25 per call) -> COMPLETED when nobody is PENDING. `stopCampaign` marks every PENDING recipient SKIPPED. Code: `src/lib/campaign-actions.ts`, `src/lib/campaign-sender.ts`.
- **Never twice:** a batch takes `lockedUntil` (90 s) with an atomic `updateMany`; each recipient is claimed (PENDING -> SENT with `sentAt`) *before* the send, and put back only on a rate limit or the daily limit (when no `messageId` was stored). A crash between claim and send misses that customer rather than doubling a message.
- **Pauses (`pausedReason`):** `DAILY_LIMIT` (`assertUnderDailyCap`, 429 `USAGE_LIMIT`), `META_RATE_LIMIT` (`isWhatsAppRateLimit`: HTTP 429 or Meta codes 4, 80007, 130429, 131048, 131056; `WhatsAppSendError` carries status and code), `TOO_MANY_FAILURES` (5 in a row in one batch), `TEMPLATE_UNAVAILABLE`.
- **Who drives it:** the Campaigns page calls `POST .../step` in a loop while SENDING (`useCampaignDriver`). The daily cron (`runDailyCampaigns` in `src/lib/automations/index.ts`, called from `/api/cron/task-reminders`) wakes `DAILY_LIMIT` pauses and works through SENDING campaigns for about 40 s. There is no per-minute scheduler; add one (a cron every minute calling the same sweep) if campaigns must finish with nobody watching.
- **Timeline and delivery:** each message creates a WhatsApp OUT activity (`Campaign: <name>`) with the Meta message id, so `recordDeliveryStatus` updates it. `campaignReport()` (`GET .../report`) reads delivery from those activities, counts replies (IN activities within 48 h of the send) and groups reasons.
- **Opt-out by reply:** `recordInbound` calls `optOutByReply()` (`src/lib/whatsapp-optout.ts`) when the whole message is STOP, UNSUBSCRIBE, CANCEL or END (`isAutoOptOutWord`). It clears the tick and record, skips PENDING campaign recipients, writes a NOTE and an audit line `whatsapp.opt_out`, and makes no reply task. This goes beyond Ivy's rule (a card a person approves) for the bare words only; the broader `asksToStop` sentences still produce a card, and a message from someone already opted out is skipped by triage as before.
- **Not built:** scheduling for later, a price estimate, a per-minute sender, recipient status updates from the webhook (use the report), and an acknowledgement message to a customer who opted out.
- **Tests:** `tests/campaigns.test.ts`, `tests/campaign-sending.test.ts`, `tests/campaign-report-optout.test.ts`.
